# Owner adoption boundary and compatibility repair

This public guide describes the dev9 repair. It contains no owner configuration,
account identifiers, credentials, stopped snapshots or actual cutover evidence.
Installation by another operator continues to default to one Standard automatic
difficulty room. Use OWNER_HUB_UPGRADE.md for an existing dev7 tester; do not use
owner adoption to reinstall or bypass the tester's ownership journal.

The owner can explicitly prepare four rooms in a separate protected installation.
That installation receives full prepared selection catalogs from the central
origin; collection and analysis remain central. Hub enrollment, directory sharing,
vote contribution and historical seeding remain separate explicit choices.
Keep independent/local weighting until eligible history is accepted and the
complete shared snapshot has been reconciled.

Before closing the working owner lobbies, the maintainer must perform a private
source/configuration preflight against the exact candidate, checking every
administrator setting and enabled integration. Saved administrator defaults are
the authority; temporary player difficulty/style/mod choices and match state do
not become replacement defaults. Retain saved personal languages, greetings,
bans, exclusions, votes, privacy settings, performance/history and required cache
state. A missing capability or unsupported source representation stops adoption.

The dev9 repair accepts valid decimal-string Discord IDs while preserving their
original stored representation. It imports the supported native SQLite columns
by name, preserving all values/types even when historical column order differs.
Only the closed supported table/column metadata is accepted; arbitrary source
DDL, views and triggers are not replayed. Native language-offer suppression is
retained alongside explicit personal language choices. These repairs do not reset
local data or relax provider authorization and ownership checks.

Actual adoption requires an approved stopped boundary, consistent SQLite online
backup including WAL, complete enumerated private state, independently checked
snapshot identity, committed import and exact configuration parity. Do not copy
an active main database alone. Configure integration/account credentials locally
through the approved private workflow; none are part of this release or sent to
the hub. A valid token and clean journal do not bypass fresh startup admission.

Never run the old and new owner controllers together on one account. A supported
cutover separately fences the old automatic deployment queue and completion
triggers, retains their state for rollback, and preserves unrelated website,
collector and analysis services. Existing tester code upgrades start no services
and preserve the same profile, catalogs, settings and recovery state.

Retain a compatible rollback export and current post-migration votes/preferences
before reverting. Do not rewind to an old backup that discards new opinions,
erase an uncertain room journal, or reuse a stale shared ratings snapshot after
a learned deletion policy. Human gameplay and integration feedback remain
separate from isolated technical qualification. Follow SHARED_HUB_TEST.md for the
agreed single-room test and return only redacted support/checklist results.
