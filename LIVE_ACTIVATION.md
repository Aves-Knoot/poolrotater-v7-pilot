# Live pilot activation — next bounded batch

The current kit is an offline rehearsal. A successful rehearsal does not prove
real OAuth, real upstream event ordering, actual room recovery or sustained
capacity. There is no operator/config/environment option to open the current
`require_live_provider()` release fence. Do not patch it out for the pilot.

## Concrete remaining coding work

1. Define a distinct approved live execution identity in the protected runtime,
   provider client/OAuth/pacing/ownership records and catalog installation.
   Reject `provider-fixture`, `provider-disabled` and rehearsal receipts as live
   authority. Use fresh installations; no implicit fixture or legacy migration.
2. Implement a supported non-fixture protected provisioning entry for the pilot
   machine, using reviewed paths and a dedicated service UID. Keep immutable
   code/environment checks, interpreter pin qualification, explicit trusted
   artifact identity, five-GiB reserve and stopped transaction/recovery rules.
   Current root provisioners and catalog initializers are fixture prototypes.
3. Connect that installed entry to the dormant fixed provider authorization and
   native room service. Recheck current official OAuth/API/referee contracts,
   account/client ownership and actual granted scopes. Preserve fixed origin,
   verified TLS, process-wide deadlines, persistent pacing and no replay of
   uncertain room creation or OAuth exchange. Prepare local-browser and SSH
   callback setup without passing secret values on command lines.
4. Provide a manually verified initial catalog import using explicit approved
   trust. Do not distribute fixture signing keys or treat a downloaded root as
   already trusted. Production signing-key custody/rotation and fleet update
   service remain distinct decisions; a manual pilot need not implement M5.
5. Provide check/configure/authorize/status/start/stop/recovery guidance and a
   bounded dedicated service unit. Install disabled/stopped first; startup never
   authorizes an account or auto-resets pacing/ownership uncertainty. Include an
   explicit privacy-safe diagnostic and removal procedure.
6. Qualify the integrated live-bound candidate without real credentials first:
   dependency/integrity/pin failures, no credential discovery, exact admission
   fences, callback/session recovery, owned process cleanup, crash/reboot,
   outage, restart and occupied/uncertain-room shutdown refusals. Use the
   authorized testing VM, never existing production units.

Removing one function's refusal is insufficient: manifests, provisioner paths,
execution identities, catalog trust and startup checks also reject live use.
These are finite release/installation changes, not missing M3 enrollment or M4
ratings features. Scope them before implementing or enabling dispatch.

## Owner/publication decisions

- Choose source/branding policy and confirm distribution rights/provenance for
  source and catalog data; exact dependency notices are prepared for review.
- Identify the new GitHub repository and private pilot/public visibility. Review
  the exported snapshot and kit, then approve the concrete publication separately.
- Choose the initial manual trust/digest delivery and later signing-key custodian.
  No initial root/key is inferred from a fixture or an untrusted download.

## Independent operator inputs for the real pilot

- Confirm Ubuntu 24.04 x86-64, Python 3.12/venv, systemd access, disk/RAM/CPU and
  whether optional .NET 8 calculations will be enabled. Debian is unqualified.
- The operator creates/owns their own OAuth client and keeps the secret and all
  tokens on their machine. Agree the expected account, exact loopback callback
  registration, local versus SSH browser flow, and requested scopes.
- Confirm account/referee room inventory and which new pilot rooms are in scope.
  Agree whether one initial room or more will be observed and who can join.
- Give explicit consent to the actual OAuth/room pilot and a test window. The
  operator logs in locally; never send credentials/codes to the central hub or
  maintainer, embed them in GitHub, or reuse the production owner's OAuth.

These inputs are needed for actual installation/authorization testing, not the
offline rehearsal or the next activation coding batch. OS/repository/license/
trust choices are separate from a request to supply account secrets now.

## Consenting pilot observation and stop criteria

Start with the agreed minimum room count. Verify authenticated account and scopes,
map eligibility, downloading/readiness/AFK starts, public/private room boundaries,
referee/client joins, commands/translations and occupied room behavior. Observe
rate-limit holds, reconnection, known-ended recovery and graceful shutdown before
expanding. Obtain consent for disruption/restart tests on these pilot rooms.
On uncertain mutation or ownership, stop and inspect; never recreate blindly or
clear journals to force progress. Keep private room details and player chat out
of shared reports. Report what was actually exercised and its observation window.

No time-based acceptance or live load claim is made by the offline kit. Production
rollout, ongoing lobbies, hub enrollment/directory and rating ingestion remain
outside this pilot preparation.
